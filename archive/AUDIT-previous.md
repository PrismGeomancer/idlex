# IDLE MVP audit — 5 October 2026

## Credibility assessment

The product's restrained typography, agent table, execution terminal, and secondary treatment of the token make it read as an infrastructure product. The original operational behavior was less convincing than the visual design: disconnected counters, fabricated comparisons, generic verification claims, and arbitrary state transitions made it feel like a dashboard animation.

The revised product is a **local agent control-plane simulation**. Its useful demonstration is registering declared capabilities, filtering eligible capacity, reserving a slot, selecting an endpoint using an explicit policy, and tracing dispatch through a terminal outcome. It does not discover idle GPU resources, independently establish an agent's capabilities, perform model inference, or operate a connected distributed network.

The UI keeps the existing warm editorial direction while giving operational evidence priority: occupied/free slots, defined endpoint RTT, routing-score breakdowns, measured phase timings, saved traces, and actionable failure states. The unsupported registered-trademark mark was removed. Decorative growth percentages and unmeasured uptime claims were removed.

- Local Chromium UI audit exercised navigation, all chart ranges, network search/empty state/capability and status filters/all sorting options, live agent dialogs, online/offline changes, custom-runtime registration, manual routing to a single-slot agent, submission locks, six visible result categories, clipboard actions, failure/retry/cancellation, refresh interruption recovery, actual paused/resumed telemetry, all documentation views, and reset cancel/confirm.

- No page runtime errors were observed in the workflow audit.
- Native browser WebMCP validation is unavailable in this session. Feature detection remains in place; native registration is not claimed as verified.

## Remaining product limitations and recommended next investment

This remains an intentionally browser-only MVP. Timers, endpoint RTTs, archived counters, background occupancy, adapter authentication, and response fixtures are simulated. The app runs one foreground task at a time and is intended for one active tab. It has no durable server scheduler, multi-user coordination, independent health validation, actual runtime adapter, authentication, or token settlement.

The most valuable next implementation would be one authenticated HTTP agent adapter backed by durable task storage: real registration/health observations, atomic slot reservation, idempotent dispatch, deadline/cancellation acknowledgments, and persisted output traces. That would provide evidence for actual coordination utility. Independent workload evaluations should follow before making claims about capability quality or routing quality. Token economics should remain proposed until useful work and payment demand are demonstrated.
